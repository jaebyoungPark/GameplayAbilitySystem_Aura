그래서 이제 이 함수도 override하면 됩니다.

이렇게 해서 두 가지 함수가 준비되면,
우리는 이제 해야 할 작업, 즉 InitAbilityActorInfo를 호출하는 것을 수행할 수 있습니다.

이제 PossessedBy 함수부터 시작하겠습니다.

기억하세요, 이 함수는 서버에서 호출되는 경우입니다.
그래서 주석을 달아 두겠습니다.

// InitAbilityActorInfo for Server

그리고 서버에서는 Player State에 접근해야 합니다.
그래서 **GetPlayerState**를 호출해야 합니다.

이때 우리는 템플릿 버전을 사용할 수 있습니다.
즉, AOrAPlayerState 타입을 전달하면, 해당 타입으로 반환됩니다.

그다음에 로컬 변수를 만들겠습니다.

AOrAPlayerState* OrAPlayerState;

그리고 이걸 if문으로 감싸서 유효한지 확인할 수도 있습니다.

if (OrAPlayerState)
{
    // 유효할 때 처리
}

사실, 이 시점에서는 null이 될 가능성이 거의 없으므로,
assert를 사용하는 편이 더 적절합니다.

check(OrAPlayerState);

이제 OrAPlayerState는 null이 아니라고 자신할 수 있습니다.

그다음, 이 Player State에서 Ability System Component를 가져옵니다.

UAbilitySystemComponent* ASC = OrAPlayerState->GetAbilitySystemComponent();

이제 Ability System Component가 준비되었으니,
InitAbilityActorInfo를 호출할 수 있습니다.

Owner Actor → OrAPlayerState

Avatar Actor → 캐릭터(this)

이렇게 전달하면 됩니다.

이 경우에는 Owner Actor가 Player State가 됩니다.

그래서 **Owner Actor에는 OrAPlayerState**를 전달하고,
**Avatar Actor에는 캐릭터 자신(this)**을 전달하면 됩니다.

이것이 바로 차이점입니다.

Ability System Component가 Player State에 있을 때 이렇게 설정해야 합니다.

하지만 이 코드를 PossessedBy에서 호출해야 하는 이유가 있습니다.

이미 유효한 Player Controller가 설정되어 있는지 확인해야 하고

Player State가 유효하고 접근 가능한 상태인지 확인해야 하기 때문입니다.

이 조건이 충족되어야만 InitAbilityActorInfo를 안전하게 호출할 수 있습니다.

이제 Player State를 확보했으니,
좋은 기회이므로 Aura Character의 Ability System Component 포인터를 설정할 수 있습니다.

AbilitySystemComponent = OrAPlayerState->GetAbilitySystemComponent();

그리고 Attribute Set 포인터도 설정합니다.

AttributeSet = OrAPlayerState->GetAttributeSet()

이제 Getter 함수들을 만들어 둔 장점이 보이기 시작합니다.

지금 우리는 서버에서 포인터를 설정했고,
Ability Actor Info도 서버에서 초기화했습니다.

하지만 클라이언트에서도 초기화해야 합니다.
그래서 OnRep_PlayerState에서 같은 작업을 수행하는 것입니다.

즉, 서버에서 했던 것과 똑같은 절차를 클라이언트에서도 반복합니다.

Player State 가져오기

체크하기

InitAbilityActorInfo 호출

Ability System Component와 Attribute Set 포인터 설정

여기서 반복 코드를 그대로 쓰는 대신,
DRY 원칙(Don’t Repeat Yourself, 반복하지 말자)을 적용합니다.

즉, 여러 줄 코드를 복사해서 붙여넣기 하지 않고,
재사용 가능한 함수 하나를 만들어서 두 곳에서 호출하는 방식입니다.

그래서 Aura Character 클래스에서 private 함수를 하나 만듭니다.

private:
    void InitAbilityActorInfoCustom();

이 함수 안에는,
서버와 클라이언트에서 반복했던 같은 코드 라인들을 넣습니다.

즉, Player State 가져오기, 체크, InitAbilityActorInfo 호출, 포인터 설정 등을 이 함수 안에 넣습니다.

이제 우리는 이 함수를 두 번 호출하면 되고,
서버와 클라이언트 모두에서 중복 코드를 제거할 수 있습니다.

이제 우리는 PossessedBy에서 이 함수를 호출할 수 있고,
OnRep_PlayerState에서도 호출할 수 있습니다.

클라이언트 쪽에서는 주석을 이렇게 달아두면 좋습니다.

// InitAbilityActorInfo for Client

만약 이 과정을 함수로 리팩토링(refactor)하지 않았다 하더라도,
괜찮습니다.
코드를 반복해도 큰 문제는 없습니다.

물론 저는 함수로 만드는 것을 권장하지만, 반드시 해야 하는 것은 아닙니다.

이제 우리는 몇 가지 중요한 목표를 달성했습니다.

Ability System Component가 자신이 누가 Owner인지 알게 됨

Owner Actor와 Avatar Actor가 명확하게 설정됨

이 설정은 앞으로 GAS(Ability System)를 계속 프로그래밍하면서 매우 유용합니다.

왜냐하면, 다양한 Ability와 GAS 클래스에서 Owner를 참조해야 할 경우가 매우 많기 때문입니다.

따라서 이 단계는 매우 중요하고 핵심적인 단계입니다.

마지막으로, 영상을 끝내기 전에 Replication Mode에 대해 다시 주목합시다.

다시 기억하세요, 우리는 플레이어가 조종하는 캐릭터의 Ability System Component를 Mixed Replication Mode로 설정했습니다.

그리고 Mixed Replication Mode를 사용할 때는 몇 가지 중요한 사항을 알고 있어야 합니다.

Mixed Replication Mode에서는 Owner Actor의 Owner가 반드시 Controller여야 합니다.

우리 경우를 보면, 플레이어가 조종하는 캐릭터에서 Ability System Component의 Owner Actor는 Player State입니다.
즉, Ability Actor Info에서 Owner Actor로 Player State를 설정했습니다.

하지만 Player State의 Owner를 따로 Controller로 설정할 필요는 없습니다.
왜냐하면 기본적으로 자동으로 설정되기 때문입니다.

Player State의 Owner는 기본적으로 자동으로 Controller로 설정됩니다.

Pawn의 경우도 PossessedBy에서 자동으로 설정됩니다.

즉, Ability System Component의 Owner Actor가 Pawn이라면,
PossessedBy에서 Pawn의 Owner가 Controller로 자동 설정됩니다.

하지만 Owner Actor가 Player State가 아니고,
Mixed Replication Mode를 사용한다면,

반드시 SetOwner를 호출해서 Owner Actor의 Owner를 Controller로 설정해야 합니다.

그래서, 지금 우리의 경우에는 걱정할 필요가 없습니다.
왜냐하면 Owner Actor가 Player State이고,
Player State의 Owner는 이미 Controller로 설정되어 있기 때문입니다.

하지만 이 점을 알고 있어야 하는 이유는,
Owner Actor가 자동으로 Owner가 Controller로 설정되지 않는 다른 클래스일 수도 있기 때문입니다.

그런 경우에는, 가능하다면 Owner를 Controller로 설정해 주어야 합니다.

물론, 어떤 Actor에 Ability System Component가 있는데 Controller가 없는 경우도 있을 수 있습니다.
그 경우에는 걱정할 필요가 없습니다.

하지만 Mixed Replication Mode에서는 Owner Actor의 Owner가 반드시 Controller여야 합니다.
이 점을 항상 염두에 두세요.

환영합니다.

이제, 우리는 방금 Ability System Component와 Attribute Set을 추가하는 데 많은 노력을 기울였습니다.

우리는 주의 깊게 Ability System Component를 Owner, Actor, 그리고 Avatar Actor와 함께 초기화했습니다.

즉, 이제 Ability System Component는 누가 자신의 오너인지 알고 있습니다.

그렇다면 Attribute Set은 어떻게 될까요?

음, 우리가 Owner Actor의 Constructor 안에서 Ability System Component와 함께 Attribute Set을 생성할 때, 지금처럼 하면 자동으로 Ability System Component에 등록됩니다.

즉, Ability System Component는 이 Attribute Set과 자신에게 등록된 다른 Attribute Set들에도 접근할 수 있습니다.

필요하다면 여러 개의 Attribute Set을 가질 수도 있습니다.

예를 들어, 속성들을 카테고리별로 여러 Attribute Set에 나누고 싶다면 그렇게 할 수 있습니다.

하지만 중요한 점은, 각각의 Attribute Set은 별도의 클래스여야 한다는 것입니다.
같은 클래스 타입의 Attribute Set을 두 개 이상 가질 수는 없습니다.

그렇지 않으면 Ability System Component에서 해당 Attribute를 가져오려고 할 때 모호성이 발생할 수 있습니다.

반대로, 모든 속성을 하나의 Attribute Set 안에 넣는 것도 전혀 문제 없습니다.

이 방법은 특히 Attribute Set이 계산을 수행할 때 다른 속성들의 값을 알아야 하는 경우 좀 더 간단하게 만들 수 있습니다.

속성(Attributes)은 차지하는 메모리가 거의 없으므로, 원한다면 프로젝트 내 모든 클래스에서 하나의 Attribute Set을 공유하고, 각 클래스에서 필요한 속성만 사용해도 됩니다.

우리의 Attribute Set은 게임 내 모든 캐릭터가 사용하는 속성들을 담게 될 것이므로, 단일 Attribute Set만 사용할 예정입니다.

하지만 앞으로를 위해 여러 Attribute Set을 가질 수 있다는 점은 기억해 두세요.

그럼, 속성(Attributes)이 정확히 무엇일까요?

속성은 게임 내 특정 엔티티(예: 캐릭터)와 연관된 숫자 값입니다.
모든 속성은 float 타입입니다.

속성들은 Gameplay Attribute Data라는 구조 안에 존재합니다.
속성들은 Attribute Set 안에 저장되며, Attribute Set은 이를 면밀히 관리합니다.

우리는 속성이 변경될 때 이를 감지하고, 원하는 기능으로 대응할 수 있습니다.

속성 값은 코드에서 직접 설정할 수도 있지만, 권장되는 방법은 Gameplay Effect를 적용해서 변경하는 것입니다.

이번 강좌에서 Gameplay Effects를 배우게 되면, Gameplay Effects가 속성 값을 여러 가지 방식으로 변경할 수 있다는 것을 곧 알게 될 것입니다.

Gameplay Effects를 사용하는 또 다른 이유는, 속성 값의 변화를 예측(Prediction)할 수 있기 때문입니다.

예측(Prediction)이란, 클라이언트가 서버의 허락을 기다리지 않고도 값이 즉시 변경될 수 있는 것을 의미합니다.
클라이언트에서 값이 바로 변경되고, 서버는 그 변화를 통보받습니다.

그 후 서버는 자신이 유효하지 않다고 판단하는 변경 사항을 롤백할 수 있습니다.

이 점은 매우 큰 장점입니다. 왜냐하면, 직접 예측 기능을 구현하려면 많은 추가 작업이 필요하기 때문입니다.

예측(Prediction)은 멀티플레이에서 더 부드러운 경험을 만들어 줍니다.
이 기능은 있을 때는 잘 느껴지지 않지만, 없으면 바로 체감됩니다.

다음은 클라이언트에서 Prediction 없이 속성 값을 변경할 때 발생하는 과정입니다.

예를 들어, 서버가 중요한 게임플레이 변경을 담당해야 하는 속성이 있다고 가정합시다.
그렇지 않으면 클라이언트가 치트를 할 수도 있습니다.

클라이언트는 서버에 속성 값을 변경해야 한다는 요청(Request)을 보냅니다.
서버는 이 요청을 받고, 개발자가 설정한 여러 기준에 따라 요청이 유효한지 판단합니다.

그리고 만약 그 변경이 유효하다고 판단되면, 서버는 확인 메시지를 클라이언트에게 다시 보내고,
클라이언트는 이제 속성 값을 실제로 변경할 수 있습니다.

하지만 데이터가 네트워크를 통해 전달되는 데는 시간이 걸리기 때문에,
클라이언트가 값을 변경하려고 한 시점과 서버로부터 허락을 받아 실제로 변경할 수 있는 시점 사이에 눈에 띄는 지연이 발생합니다.

지연 시간(Lag)이 100밀리초 이상까지 도달하는 것도 흔하며,
게임에서 어떤 행동을 수행하고 나서 그 행동의 결과를 보고 듣는 데까지 지연이 생기면,
이는 매우 좋지 않은 게임플레이 경험을 만들게 됩니다.

그럼 이번에는 Prediction이 있을 때 어떻게 되는지 살펴보겠습니다.

GAS(Ability System)에서 Prediction이 적용되면, Gameplay Effect가 클라이언트 측에서 속성을 수정하고,
그 변경은 즉시 클라이언트에 반영됩니다.

즉, 지연이 전혀 없습니다.

그 후, 이 변경 사항은 서버로 전송되며, 서버는 여전히 변경 사항의 유효성을 검증할 책임을 갖습니다.

만약 서버가 이 변경이 유효하다고 판단하면,
좋습니다! 서버는 다른 클라이언트에게도 변경 사항을 알릴 수 있습니다.

하지만 서버가 이 변경이 유효하지 않다고 판단하면,
예를 들어, 클라이언트가 게임을 해킹해서 비정상적으로 큰 데미지를 주려고 시도했다면,
서버는 그 변경을 거부하고 롤백할 수 있으며, 클라이언트의 값을 서버 기준으로 되돌릴 수 있습니다.

다시 올바른 내용으로 돌아가겠습니다.

서버는 여전히 권한(Authority)을 가지고 있지만, 클라이언트는 지연 없이 바로 반응할 수 있습니다.

Prediction은 복잡하지만, GAS에 내장 기능으로 제공되기 때문에 큰 장점이 있습니다.
이 덕분에 우리는 게임플레이 메커니즘 제작에 집중할 수 있고, 지연 보정(Lag Compensation)을 직접 구현할 필요가 없습니다.

그럼 속성(Attribute)이란 무엇일까요?

속성은 Gameplay Attribute Data 타입의 객체이며, Attribute Set에 저장됩니다.

속성은 실제로 두 가지 값을 가집니다: Base Value(기본 값)와 Current Value(현재 값)입니다.

Base Value: 속성의 영구적인 값입니다.

Current Value: 기본 값에 Gameplay Effect로 인한 임시 수정값을 더한 값입니다.

이것을 버프와 디버프(Buff/Debuff) 관점에서 생각해 보세요.
예를 들어, 특정 시간 동안 값을 더하거나 빼는 효과가 있을 수 있습니다.
그 시간이 지나면 수정값은 제거되고, 속성은 다시 Base Value로 돌아갑니다.

자, 이제 Base Value가 속성의 최대값(Max Value)이라고 결론 내리고 싶은 유혹이 있을 수 있습니다.

예를 들어, 체력 바(Health Bar)의 퍼센트를 계산할 때, Current Value를 Base Value로 나누면 될까요?

음, 아니요.
이것은 흔한 실수이며, 올바른 방법이 아닙니다.

속성의 최대값(Max Value)은 속성 자체와 별개입니다.

최대값은 변할 수 있는데, 이는 꽤 흔한 상황입니다.
따라서 최대값은 자체의 별도 속성(Attribute)으로 만드는 것이 좋습니다.

이렇게 하면, Gameplay Effect를 속성 자체에 적용할 수도 있고,
최대 속성(Max Attribute)에 별도로 적용할 수도 있습니다.

예를 들어, 체력 바의 퍼센트는 현재 체력 / 최대 체력으로 간단히 계산할 수 있습니다.

이제 속성이 무엇인지 알았으니,
다음 단계는 Attribute Set에 실제 속성을 추가하는 것입니다.
이 작업을 바로 진행하겠습니다.

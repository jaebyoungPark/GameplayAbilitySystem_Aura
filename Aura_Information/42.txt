이제 먼저 설명해야 할 것은
Stacking Type의 두 가지 옵션입니다.

Aggregate by Source

Aggregate by Target

이 두 옵션이 무엇을 의미하는지 살펴보겠습니다.

이것들이 어떻게 동작할까요?

먼저 Stacking Type 옵션에서 None을 제외한 첫 번째 옵션은 Aggregate by Source입니다.

이것이 어떻게 작동하는지 살펴봅시다.

예를 들어 Stack Limit Count를 2로 설정했다고 가정해 보겠습니다.

Aggregate by Source의 의미는
스택 제한이 Source(효과를 적용하는 주체) 기준으로 적용된다는 것입니다.

즉,

어떤 Source가 Target에게 Gameplay Effect를 적용하면
이것은 1개의 스택으로 계산됩니다.

그리고 이 스택은 Source 기준으로 집계(aggregate) 됩니다.

그래서 이 시점에서 해당 Source는 Target에게 이 Gameplay Effect를 1스택 적용한 상태가 됩니다.

이제 같은 Source가 동일한 Gameplay Effect를 다시 적용했다고 합시다.

그러면 이것은 두 번째 스택으로 계산됩니다.

그리고 이것 역시 Source 기준으로 집계됩니다.

이 시점에서 우리는 Gameplay Effect의 스택이 2개가 되었고
이것이 바로 우리가 설정한 최대 스택 수입니다.

왜냐하면 Stack Limit Count를 2로 설정했기 때문입니다.

이제 같은 Source가 다시 같은 Effect를 적용하려고 하면
그것은 세 번째 스택이 됩니다.

하지만 이것은 설정된 스택 제한을 초과합니다.

따라서 이 Effect는 더 이상 적용될 수 없습니다.

여기서 중요한 점은 우리가 Source 기준으로 집계하고 있다는 것입니다.

즉,

각 Source는 자신이 발생시킨 이 Effect의 스택 수를 따로 관리합니다.

이제 게임 안에 또 다른 Source가 등장해서 동일한 Gameplay Effect를 적용했다고 가정해 봅시다.

우리는 Source 기준으로 스택을 집계하고 있기 때문에

이 새로운 Source에게는
이것이 첫 번째 스택이 됩니다.

그래서 이 스택은 그 Source 기준으로 집계됩니다.

결과적으로

첫 번째 Source → 2 스택

두 번째 Source → 1 스택

이렇게 됩니다.

겉보기에는 총 3 스택이 되어 스택 제한을 넘는 것처럼 보일 수 있습니다.

하지만 우리는 Source 기준으로 집계하고 있기 때문에

각 Source는 Target에게 최대 2스택까지 적용할 수 있습니다.

이제 다른 옵션인 Aggregate by Target과 비교해 봅시다.

아까는 Source 기준으로 집계했지만
이제는 Target 기준으로 집계합니다.

예를 들어

어떤 Source가 Gameplay Effect를 적용하면

이것은 1개의 스택으로 계산됩니다.

하지만 이번에는 Source가 아니라 Target 기준으로 집계됩니다.

이제 같은 Source가 다시 Effect를 적용하면

이것은 두 번째 스택이 되고

이 스택은 Target 기준으로 집계되는 전체 스택 수에 추가됩니다.

이제 같은 Source가 또 하나의 스택을 적용하려고 시도할 수 있습니다.

그러면 그것은 세 번째 스택이 되겠죠.

하지만 당연히 이것은 Stack Limit Count를 초과합니다.

따라서 예상한 것처럼 이 스택은 적용될 수 없습니다.

그런데 이번에는 또 다른 Source가 이 효과를 적용하려고 등장합니다.

만약 우리가 Source 기준으로 집계(Aggregate by Source) 하고 있었다면
이 새로운 Source는 아직 아무 스택도 적용하지 않았기 때문에 스택을 적용할 수 있었을 것입니다.

하지만 지금은 Target 기준으로 집계(Aggregate by Target) 하고 있습니다.

이미 Target에게는 두 개의 스택이 적용된 상태입니다.

따라서 이 새로운 Source가 Effect를 적용하려고 하면

이것은 Target 기준으로 세 번째 스택이 됩니다.

하지만 Stack Limit Count는 2이기 때문에

이것은 제한을 초과하게 됩니다.

그래서 이 Effect는 적용될 수 없습니다.

이것이 바로 Aggregate by Source와 Aggregate by Target의 차이입니다.

정리하면

Aggregate by Source
→ Source마다 스택 제한이 따로 존재

Aggregate by Target
→ Target 전체 기준으로 스택 제한이 존재

이제 예제를 보겠습니다.

우리의 경우 Aggregate by Source를 선택하고
Stack Limit Count를 2로 설정했다고 가정합니다.

이제 Stack Expiration Policy의 마지막 옵션을 살펴보겠습니다.

그 옵션은 Refresh Duration입니다.

이 옵션의 의미는 다음과 같습니다.

스택이 만료될 때 지속 시간을 다시 갱신합니다.

심지어 스택이 하나뿐이어도 갱신됩니다.

즉,

이 효과는 사실상 무한 지속 효과가 됩니다.

왜냐하면

지속 시간이 끝날 때마다 계속 다시 시작되기 때문입니다.

설명에도 이렇게 적혀 있습니다.

“이 옵션은 on stack count change callback을 통해
스택 감소를 직접 처리할 때 사용할 수 있습니다.”

즉,

스택 수가 변경될 때 반응하는 시스템을 따로 구현할 수 있습니다.

이 부분은 나중에 배우게 됩니다.

예를 들어 Refresh Duration으로 설정하고
크리스탈 하나만 주워보겠습니다.

그러면 마나 증가가 계속 이어지고 절대 멈추지 않습니다.

왜냐하면

스택이 만료될 때마다 지속 시간이 다시 갱신되기 때문입니다.

그래서 이것은 무한 지속 주기 효과(Periodic Effect) 를 만드는 방법 중 하나입니다.

하지만 여기서는 다시

Clear Entire Stack으로 설정하겠습니다.

이렇게 하면

여러 개의 크리스탈을 주웠을 때도

지속 시간이 끝나면 모든 스택이 한 번에 제거됩니다.

마무리하기 전에 하나 더 설정해 보겠습니다.

Crystal Heal Gameplay Effect로 가서
스태킹 설정을 해보겠습니다.

다음과 같이 설정합니다.

Stacking Type
→ Aggregate by Target

Stack Limit Count
→ 1

그리고 Crystal Mana와 동일하게

Refresh on Successful Application

Reset on Successful Application

을 사용합니다.

또한

Stack Expiration Policy도
→ Clear Entire Stack

으로 설정합니다.

이렇게 하면

한 번에 너무 많은 크리스탈을 주웠을 때 효과가 과도하게 적용되는 것을 방지할 수 있습니다.

즉, 일종의 속도 제한(throttling) 역할을 합니다.

좋습니다!

이제 우리는 Gameplay Effect의 스태킹(Stacking) 에 대해 배웠습니다.

다음 영상에서 다시 만나겠습니다.
